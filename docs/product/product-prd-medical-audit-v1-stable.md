# AI智能审计管理系统 V1.0 PRD

## 1. 产品定位

AI智能审计管理系统 V1.0 是面向公立医院内审场景的私有化医疗/医保合规审计 MVP。

首版不做通用 SaaS、不做开放式 AI 聊天工具、不做多院多租户平台。产品目标是先在单院环境内，以门户化审计工作台承载一条可验收闭环：

```text
知识依据查询 -> HIS 数据审计 -> 疑点识别 -> 人工复核 -> 底稿/报告 -> 整改跟踪
```

当前仓库已先行实现的是“知识库查询引擎”子系统，用于法规、目录、监管规则和负面清单的检索、引用型回答、原文预览和索引发布验收。它是 V1.0 的知识支撑层，不等同于完整审计判定系统。

前端产品形态调整为参考系统式“AI 审计应用门户”：左侧主导航、顶部多标签工作区、历史对话、智能体、知识库、文档检索、AI 数据分析、知识图谱、底稿报告和项目管理共同构成统一入口。门户化只改变用户入口和工作组织方式，不改变审计结论必须可追溯的证据链要求。

## 2. 业务目标

### 2.1 V1.0 必须达成

- 在单院私有化环境内完成可演示、可试运行的医疗/医保审计 MVP。
- 以 `AI智能审计管理系统` 为统一前端品牌，提供参考系统式审计门户和多标签工作区。
- 支持提示词型审计智能体：一个智能体对应一个提示词，可新增智能体，但不做复杂多步工具编排。
- 支持上传表格进行 AI 数据分析，并保留审计数据分析入口。
- 项目管理必须包含成员管理能力，至少展示项目成员、角色和新增成员入口。
- 知识库首期区分个人知识库、系统知识库和公开知识库，但先以只读展示为主。
- 仅接入 HIS 数据，完成一个首选细分审计场景的 0/1 合规判定。
- 每条疑似问题必须能追溯到规则、原始数据、计算过程和知识依据。
- 审计员可完成复核、底稿沉淀、报告导出和整改状态跟踪。
- 系统支持本地部署、权限控制、审计日志和离线内容/规则更新。

### 2.2 V1.0 不承担

- 不接入 LIS、PACS、财务系统。
- 不做医保局监管协同平台。
- 不做多院多租户。
- 不做移动端。
- 不做复杂多轮智能体编排；首期智能体限定为提示词型审计助手。
- 不把生成模型回答作为无证据审计结论。

## 3. 目标用户与权限角色

| 角色 | 主要诉求 | V1.0 权限边界 |
| --- | --- | --- |
| 一线审计员 | 查询依据、发起审计、复核疑点、生成底稿 | 查询、创建任务、复核、导出草稿 |
| 审计科主任/负责人 | 审核结论、签字验收、跟踪整改 | 审核确认、正式报告导出、整改闭环确认 |
| 医院信息科 | 提供 HIS DDL、测试数据、部署环境 | 数据接入协作、系统运维协助 |
| 业务/审计专家 | 确认规则口径、报告模板和验收标准 | 规则复核、评测集复核、模板确认 |
| 系统管理员 | 索引发布、回滚、用户与基础配置 | 索引管理、运行状态、日志查看 |

### 4.1 当前已落地子系统：知识库查询引擎

当前代码仓库已形成以下能力：

- `Next.js` 今日工作台、API-first 查询工作台和疑点清单，以及 `FastAPI + Jinja + CSS` 后端兼容工作台。
- `/knowledge-query` Next 原生查询工作台已接入 `POST /api/v1/query`；`/pages/query` 保留为后端兼容查询页。
- `/findings` Next 原生疑点清单已接入 `GET /api/v1/audit-findings`，支持统计、复核状态筛选、证据项展示、生成链路就绪诊断和复核任务创建入口；`/pages/audit-findings` 保留为后端兼容疑点页。
- `/pages/chat` 对话审证台、`/pages/review-tasks` 复核任务台、`/pages/index-admin` 索引管理页、`/pages/preview/{chunk_id}` 原文预览页。
- `/pages/chat/export` 支持当前单轮对话的 Markdown/JSON 审计底稿导出。
- `/pages/review-tasks` 支持把单轮对话回答创建为 PostgreSQL 任务级复核记录，维护复核状态、意见、结论，并导出任务级 Markdown/JSON 记录。
- `data/医保审核前期资料` 的抽取、切分、BM25 + vector 检索、引用型 fallback answer。
- PostgreSQL + pgvector active index version 查询与状态隔离。
- Kimi embedding 主索引已导入：`486` 个 indexed documents、`48985` 个 chunks、`48985` 个 embeddings、`13` 个 pending files。
- 固定检索评测集 V1：`52` cases；fallback 答案评测集 V1：`8` cases。
- `audit_log_events` 已作为操作日志持久化底座接入，`record_operation` 可将查询、导出、索引管理和复核任务操作同步写入数据库；`/pages/audit-logs`、`/audit/logs`、`/audit/logs/export` 已支持按任务、用户、动作和时间范围查询与导出，并限制为 `it-admin` 和 `department-head` 可读导出，响应和导出已执行 response-only 敏感字段脱敏；`audit-log-retention` CLI 已支持保留期 dry-run 计划、显式原始 JSONL 归档、归档 `sha256` 和归档后数据库清理；审计日志归档已支持 archive root 标准目录布局、detached HMAC-SHA256 签名 manifest、上一签名 `sha256` 链式留痕、只读验签、archive root 巡检报告和生产侧只读巡检脚本。

### 4.2 当前未落地但属于 V1.0 的子系统

- HIS 数据接入与任务级数据快照。
- 结构化规则表、规则版本、医院本地覆盖规则。
- 多项目/案件级疑点治理、PostgreSQL 案件级人工复核台和案件级整改归档流。
- 提示词型智能体管理、上传表格 AI 数据分析、项目成员管理和门户化多标签工作区。
- 用户、角色、科室关系初始化、全站权限控制、证书级非对称电子签章和长期留存介质策略。

### 4.3 当前不能被写成已完成的能力

- Kimi Code 当前可作为 embedding provider 使用，不能被写成已验证可用的线上答案生成模型。
- Anthropic answer provider 当前预检未通过，不能被写成可用生产生成模型。
- 当前 `/pages/chat` 是单轮对话审证工作台，不能被写成服务端持久化多轮会话系统。
- 当前 `/pages/review-tasks` 是任务级 PostgreSQL 复核任务台，虽已具备任务级报告门禁、报告签发、整改跟踪和结案门禁 fixture 验证，但不能被写成生产级案件系统、多实例强一致复核流、证书级电子签章或真实医院整改验收系统。
- 增量计划目前支持影响分析和发布链路设计，不能把“新增源文件后自动生产级增量写入”写成已完成能力。

### 4.4 门户化信息架构

V1.0 前端目标信息架构采用参考系统式审计门户：

| 模块 | V1.0 定义 | 首期边界 |
| --- | --- | --- |
| AI 对话 | 审计人员自然语言入口，支持选择提示词型智能体、附件、引用依据和可追溯回答 | 复用现有对话审证能力，保留引用、证据质量和原文预览 |
| 我的智能体 | 用户创建或收藏的提示词型审计智能体 | 一个智能体对应一个提示词，支持新增、编辑、分类和关联知识库/项目 |
| 智能体广场 | 审计智能体模板市场 | 仅展示医疗/医保审计相关模板；财政、农业、国企、采购等专题只作为 UI 参考 |
| 知识库 | 个人、系统、公开知识库的业务化展示 | 首期只读展示，运维类索引发布和回滚仍在索引管理 |
| 文档检索 | 面向文档和知识库的统一检索首页 | 支持搜索历史、库分类、对话文档、知识库文档和引用原文入口 |
| AI 数据分析 | 上传表格分析和审计数据分析入口 | 必须具备表格上传分析演示闭环，同时承接 HIS staging、规则运行和疑点统计 |
| 知识图谱 | 展示项目、文档、规则、疑点、复核和整改之间的关系 | 首期可做只读图谱列表或静态预览，复杂交互后置 |
| 审计底稿/报告 | 历史生成记录、底稿生成、报告签发和整改导出入口 | 复用复核任务台深层能力，新增报告首页 |
| 项目管理 | 项目列表、项目空间和成员管理 | 必须包含成员列表、角色展示和新增成员入口 |

门户化 UI 的硬性要求：

- 左侧固定主导航包含上述 9 个模块。
- 顶部提供多标签工作区，支持打开、切换和关闭标签。
- 顶部栏显示当前页面标题和用户入口。
- 左侧保留历史对话入口。
- 不在普通业务页面暴露低层工程术语，如 `API-first`、`store`、`backend`、`persistent`。

## 6. 数据与证据链要求

V1.0 的所有审计结论必须满足可追溯：

- 知识依据追溯到 `source_package_version_key`、`index_version_key`、`chunk_id`、源文件 locator。
- HIS 审计结果追溯到数据快照版本、规则版本、运行批次和复核记录。
- 报告结论追溯到确认违规明细、底稿记录和整改事项。
- 生成模型只能辅助组织语言，不能成为无来源审计结论。

## 8. V1.0 验收标准

### 8.1 知识库查询引擎验收

- 可索引文件成功率不低于 `95%`，无法处理文件进入 pending 或 failed 队列。
- 当前 active Kimi 主索引可查询，embedding 计数与 active indexed documents 匹配。
- 固定 `52` 条检索评测达到当前内部基线。
- 固定 `8` 条 fallback 答案评测达到当前内部基线。
- 每条回答必须提供引用和原文预览入口。

### 8.2 HIS 审计链路验收

- 使用医院提供的 HIS DDL 和脱敏历史数据完成首个专项审计任务。
- 系统输出疑点清单和每条疑点的最小证据包。
- 审计员能完成复核并导出底稿。
- 负责人能确认报告并进入试运行。
- 准确率指标必须先定义口径；不能只写“92%”而不说明按条目、问题、病例还是案件计算。

### 8.3 试运行验收

- 试运行周期：`1` 个月。
- 试运行期间记录 P0/P1 问题、响应时间、修复记录和复测结果。
- 试运行结束后由审计员和负责人签字确认是否正式割接。

## 9. 外部依赖与待确认事项

以下事项不阻塞 PRD 基线落地，但阻塞 V1.0 详细排期和验收闭环：

- 首个细分审计场景：诊疗合规、收费合规、医保资金使用或参保人员审计中的哪一个。
- HIS 对接方式：中间库比对还是直接抽取；当前建议优先中间库。
- HIS DDL、字段字典、脱敏历史数据和测试集交付时间。
- 医院现有审计报告模板和签字流程。
- 规则库维护责任：产品方、医院审计科、信息科或联合维护。
- 准确率验收口径和抽样方法。
- 私有化部署目标环境、网络隔离要求和等保约束。
