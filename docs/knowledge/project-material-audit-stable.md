# 项目资料审计与归类结论

## 1. 审计对象

本次审计仅覆盖当前仓库已有材料，不对外部需求做额外假设。

仓库当前规模结论：

- 仓库总量约 `716M`
- `data/医保审核前期资料/` 约 `528M`
- 其中 `全量法律` 约 `311M`
- `医保目录` 约 `41M`
- `智能监管“两库”规则和知识点` 约 `74M`
- `风险负面清单` 约 `6.8M`

## 2. 项目目的判定

从现有材料交叉比对后，当前项目目的可以明确为：

- 构建一个面向医院审计场景的 AI 辅助审计系统
- 首版目标不是泛行业平台，而是尽快跑通单院医疗/医保审计 MVP
- 核心价值不在“大模型聊天”，而在“把审计知识、审计规则、审计数据和审计交付连起来”

## 3. 项目属性判定

### 3.1 不是哪类项目

- 不是通用知识库工具
- 不是纯算法验证项目
- 不是仅供展示的 PPT 项目
- 不是一开始就做多系统、多场景、多租户的平台产品

### 3.2 它实际是哪类项目

- 私有化部署的垂直审计产品
- 行业知识密集型产品
- 数据接入和规则解释同等重要的合规产品
- 带明显项目制交付特征的产品化项目

## 6. 数据资产判定

`data/医保审核前期资料/` 应视为正式输入资产区，不是 `tmp/`，也不是草稿目录。

当前可识别的四类核心资料：

- `全量法律`
  作用：法规与政策基础语料
- `医保目录`
  作用：医保目录、DRG/DIP、编码等结构化约束资料
- `智能监管“两库”规则和知识点`
  作用：国家医保智能监管规则库和知识库输入源
- `风险负面清单`
  作用：高风险问题样本与规则补充输入

当前不建议对 `data/` 内 17k+ 文件做批量重命名，原因有二：

- 这已经属于“资料库治理”而不是“项目初始化”
- 大规模改名会破坏原始来源痕迹，影响后续溯源和校验

## 7. 当前准备度结论

- git 仓库初始化
- 标准目录骨架建立
- 根目录正式材料归位

### 7.2 仍缺失

## 8. 对后续工作的直接约束

后续 PRD 和技术设计必须遵守以下判断：

- 先以单院 MVP 为边界，不按泛平台写需求
- 先以 HIS-only 为边界，不默认扩到多系统
- 先以 0/1 合规判定为边界，不预设复杂评分体系
- 先验证首个细分审计场景，不把“两库四审”全部平铺进同一个版本
