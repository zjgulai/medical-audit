# 前端全量重构设计规格：机构自查工作台 OS

## 1. 目标

将当前知识库网站从“查询页面集合”重构为面向医院/机构自查人员的医保审计自查工作台。

产品目标不是单纯美化页面，而是形成完整闭环：

```text
政策问答 → 材料自查 → 疑点生成 → 补证整改 → 底稿/报告 → 项目归档
```

## 2. 已确认决策

| 决策项 | 结论 |
|---|---|
| 重构范围 | 全量前端设计，分模块连续开发 |
| 主用户角色 | 医院/机构自查人员 |
| 默认工作流 | 政策问答、材料自查、补证整改三段式闭环 |
| 前端技术路线 | 新建 React/Next.js 前端应用，后端保留 FastAPI API 服务 |
| 全局布局 | 自查工作台 OS |
| 主导航 | 流程闭环导航 |
| AI 对话骨架 | 自查向导 + 多轮对话 + 证据侧栏 |
| 模块范围 | 全模块真实功能，不只做占位 |
| 核心对象 | 自查项目/案件驱动 |
| 迁移路线 | Next.js 新前端 + FastAPI API 化 + 旧版 Jinja 页面保留兜底 |

## 3. 架构设计

采用双轨迁移架构：

```text
Next.js Frontend
  ├─ 今日工作台
  ├─ AI 引导自查
  ├─ 专题规则库
  ├─ 材料与文档检索
  ├─ 疑点清单
  ├─ 补证整改
  ├─ 底稿/报告
  ├─ AI 数据分析
  ├─ 知识图谱
  └─ 项目档案

FastAPI Backend
  ├─ 现有 RAG 查询 API
  ├─ 规则卡 rerank API
  ├─ 文档预览 / 引用溯源 API
  ├─ 复核任务 API
  ├─ 索引状态 API
  └─ 新增项目 / 会话 / 材料 / 疑点 / 报告 / 图谱 / 分析 API
```

旧版 Jinja 页面在迁移期间继续保留，作为生产兜底入口。新版前端不直接复刻旧页面，而是围绕自查项目组织功能。

## 4. 全量模块

### 4.1 今日工作台

默认首页，展示当前自查项目、待处理疑点、补证任务、最近会话、索引健康、风险趋势和快捷入口。

### 4.2 AI 引导自查

核心入口，采用三栏结构：

```text
自查向导 | 多轮 AI 对话 | 证据侧栏
```

功能包括政策问答、材料自查、缺失条件追问、规则卡命中、引用原文、证据质量、疑点生成和补证建议。

### 4.3 专题规则库

展示医保基金使用合规、身份骗保、收费合规、诊疗合规等专题。规则卡同时支持 Markdown 和 JSON 展示，并呈现适用地区、证据状态、生命周期状态和规则来源。

### 4.4 材料与文档检索

统一管理源文档、机构上传材料、原文预览、全文检索、向量检索、引用定位和材料归档。

### 4.5 疑点清单

把 AI 识别出的风险点结构化，包含风险等级、规则依据、证据强度、待补条件、处理状态和人工确认状态。

### 4.6 补证整改

围绕疑点生成补证任务、整改建议、责任人、截止时间、处理记录、复核意见和关闭原因。

### 4.7 底稿/报告

生成自查底稿、整改记录、专题报告。报告必须保留规则卡、引用、原文片段、人工确认链和审计日志。

### 4.8 AI 数据分析

围绕自查项目输出风险分布、疑点趋势、材料覆盖度、规则命中热区和整改进度。该模块需要新增后端聚合 API。

### 4.9 知识图谱

展示机构、人员身份、医保基金支付、规则卡、材料、疑点、整改任务之间的关系。该模块需要新增图谱数据接口，第一阶段可从项目内结构化数据生成。

### 4.10 项目档案

管理自查项目/案件，沉淀项目画像、会话、材料、疑点、任务、报告和操作日志。

## 5. 核心对象与状态机

核心对象为 `self_check_project`。所有会话、材料、规则命中、疑点、补证任务、整改记录和报告都必须归属到一个自查项目。

AI 引导自查状态机：

```text
intake 收集条件
  → retrieve 检索规则与证据
  → analyze 形成判断
  → clarify 缺证追问
  → finding 生成疑点
  → remediation 生成整改建议
  → report 汇总输出
```

每条 AI 输出必须标记判断性质：

```text
政策解释 | 风险提示 | 疑点草稿 | 待人工确认 | 已确认疑点 | 已整改 | 已关闭
```

## 6. 前后端联调边界

第一阶段复用现有能力：

- RAG 查询与引用返回。
- 规则卡 rerank 和命中解释。
- 文档预览与原文溯源。
- 复核任务创建与状态流转。
- 索引状态检查。

新增 API 以模块为边界逐步补齐：

- 项目 API：创建、查询、更新、归档自查项目。
- 会话 API：多轮上下文、步骤状态、追问记录。
- 材料 API：上传、关联、检索、引用定位。
- 疑点 API：生成、确认、关闭、转补证任务。
- 整改 API：补证、处理、复核、关闭。
- 报告 API：底稿生成、报告导出、引用链校验。
- 分析 API：风险分布、趋势、覆盖度和整改进度。
- 图谱 API：项目内实体关系和证据链关系。

## 7. 安全与审计边界

系统不得把 AI 草稿包装成确定审计结论。生成内容必须按证据等级和人工确认状态展示：

```text
AI 草稿 → 待补证 → 待人工确认 → 已确认疑点 → 已整改/已关闭
```

处理规则：

- 证据不足时，只输出风险提示和需补证条件。
- 引用缺失时，禁止进入正式底稿。
- 规则卡冲突时，展示冲突条件并要求人工确认。
- 地区政策不明时，只按国家和资料内明确地区政策回答，不外推。
- 模型或 API 失败时，保留用户输入和检索结果，允许重试。
- 索引未就绪时，禁用疑点生成，但允许浏览规则卡和文档。
- 所有生成疑点、确认疑点、关闭疑点、生成报告和导出报告动作必须记录审计日志。

## 8. UI/UX 方向

视觉风格必须服务于医保审计的严肃性，不采用消费级强刺激设计。

设计原则：

- 克制、专业、政务/医疗审计质感。
- 信息密度高但层级清楚。
- 左侧流程导航稳定，顶部项目上下文稳定。
- AI 输出区必须突出结论性质、引用来源和下一步动作。
- 高风险状态使用标签、边框和局部强调，不使用大面积红色。
- 空状态必须提供明确下一步，而不是装饰性插画。
- 加载态、错误态、证据不足态、索引未就绪态必须完整设计。

## 9. 测试与验收

每个模块按以下 gate 验收：

```text
设计验收 → API 契约验收 → 前后端联调 → E2E 流程 → 证据文件落盘 → 人工确认
```

验收维度：

- UI：布局、导航、空状态、加载态、错误态、移动端基本适配。
- API：schema 稳定、错误码明确、关键字段可追溯。
- 业务：政策问答、材料自查、疑点生成、补证整改、报告导出形成闭环。
- 证据：每个 AI 结论都有来源、规则卡、原文片段和证据质量。
- 回归：旧版 `/pages/chat`、`/pages/query`、`/pages/index-admin` 迁移期间仍可用。
- E2E：覆盖创建项目、引导对话、命中规则卡、查看引用、生成疑点、创建补证任务、导出底稿。
- 生产：本地通过后再部署腾讯云容器，验证健康检查、核心 API、页面首屏和真实查询链路。

## 10. 分模块开发顺序

1. Next.js 基座、设计系统、路由壳层。
2. 自查项目模型与今日工作台。
3. AI 引导自查与多轮会话。
4. 专题规则库与规则卡展示。
5. 材料与文档检索。
6. 疑点清单。
7. 补证整改。
8. 底稿/报告。
9. AI 数据分析。
10. 知识图谱。
11. 项目档案与审计日志收口。

## 11. 不做事项

- 不在第一阶段删除旧版 Jinja 页面。
- 不把 AI 输出直接标记为确定违规。
- 不做无项目归属的孤立聊天记录。
- 不做只有视觉壳、没有业务闭环的智能体广场。
- 不绕过引用和规则卡生成正式底稿。

## 12. 待下一步计划拆解

本规格通过复核后，进入实施计划拆解。计划需要明确每一阶段的文件边界、API 契约、测试命令、E2E 场景和验收证据路径。
