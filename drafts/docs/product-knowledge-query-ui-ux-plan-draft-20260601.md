# 知识库查询 UI/UX 方案草稿

## 1. 产品定位修正

当前界面不应继续按“通用聊天页”设计。这个产品的真实定位是医保审核证据工作台：

- 用户不是普通问答用户，而是需要形成判断、复核证据、追溯原文的审核人员。
- 系统不是聊天机器人，而是把 `data/` 知识库转化为可查询、可引用、可复核证据链的审证工具。
- 页面目标不是让回答看起来像聊天，而是让每个结论都能快速回到依据、适用条件和风险边界。

因此 `/pages/chat` 的核心名称应理解为“对话审证台”，而不是“聊天窗口”。

## 2. 当前问题复盘

### 2.1 产品模型问题

当前页面仍然是“查询表单 + 回答文本 + 引用列表”的组合，没有形成完整审证流程：

- 用户输入后缺少明确的案件上下文、追问路径和复核动作。
- 回答正文与证据引用没有强绑定，用户需要自己在正文和右侧证据之间来回比对。
- 最近对话只是日志列表，不是可继续工作的会话记忆。
- 来源过滤被折叠在普通表单里，业务重要性不足。

### 2.2 视觉系统问题

当前视觉有暗色英雄区和卡片，但还不是品牌系统：

- `AuditScope` 只是文本标识，缺少稳定的 logo mark、语气、组件语法和视觉隐喻。
- 大面积英雄区占据首屏，但真正的工作台区域密度不足。
- 三栏布局存在，但左、中、右信息权重不清，用户注意力被平均分散。
- 回答展示使用接近原始文本的方式，缺少专业报告感。

### 2.3 审计回答问题

医保审核场景需要的是结构化审证结果，而不是普通自然语言段落：

- 先给结论摘要。
- 再给证据链。
- 明确适用条件。
- 明确风险和不确定性。
- 给出下一步人工复核动作。
- 每个关键判断必须能落到引用和原文预览。

### 2.4 工程体验问题

页面曾出现 `127.0.0.1:8010/pages/chat` 拒绝连接，说明本地服务体验仍有脆弱点：

- 服务启动依赖环境变量和手动命令，缺少面向开发者的稳定入口。
- 后端未加载时页面只给提示，没有把恢复路径做成清晰操作流。
- 当前测试只验证文案存在，无法防止 UI 退回粗糙状态。
- 缺少截图基线和视觉验收流程。

## 3. 设计方向

采用“Evidence Command Center”方向：克制、专业、具有证据室和审计台账质感。

- 顶部：压缩为工作台导航与运行状态，不再使用占屏过大的营销 hero。
- 左侧：案件/会话轨道，展示最近问题、推荐追问和当前审证阶段。
- 中间：对话与结论工作区，突出结构化回答、引用标记和复核动作。
- 右侧：证据卷宗，按法规、规则、目录、风险案例分组展示依据。
- 视觉：深墨绿作为可信底色，锈红作为风险与操作强调，账册暖纸色作为内容承载。

## 4. `/pages/chat` 改造要求

### 4.1 首屏结构

首屏应直接进入工作台，而不是先展示营销口号：

- 顶部品牌栏保留 `AuditScope`，增加“证据工作台”语义。
- 增加运行状态摘要：检索后端、引用约束、原文预览、人工复核。
- 后端未加载时，提示必须包含恢复路径：进入索引管理页加载后端。

### 4.2 对话区

对话区应提供完整工作流：

- 无问题时展示审证空状态和推荐问题。
- 有问题时展示审计员问题。
- 有回答时展示结构化“审证结论卡”，避免直接裸露 `<pre>`。
- 输入区应更像 command composer，提供来源过滤和主操作按钮。

### 4.3 证据区

证据区应从“引用列表”升级为“证据卷宗”：

- 质量卡展示置信度、引用数、证据分组数。
- 每个分组使用清晰标题和编号。
- 每条证据展示引用编号、摘要、原文入口。
- 无证据时明确说明系统不会生成无引用结论。

### 4.4 左侧会话区

左侧不应只是日志：

- 展示当前审证流程阶段。
- 展示最近问题及引用数量。
- 展示推荐追问，帮助用户继续向适用条件、凭证核验、审核清单推进。

## 5. 验收标准

- `/pages/chat` 在未输入问题时也像完整产品，而不是空表单。
- 回答区不再使用裸 `pre` 作为主要展示。
- 证据区能明确区分质量、分组、引用、原文入口。
- 后端未加载状态能给出恢复路径。
- 桌面三栏结构有明确主次，移动端能自然堆叠。
- `tests/knowledge_query/test_pages.py` 至少覆盖工作台、审证结论、证据卷宗和推荐追问关键结构。
- 在可用截图工具恢复后，补充截图基线并用视觉评审进行迭代。

## 6. 当前阶段执行边界

本阶段只改造现有 `FastAPI + Jinja + CSS` 页面，不引入 Next.js 或复杂前端状态。

优先级：

1. 先修正 `/pages/chat` 的产品结构和视觉系统。
2. 再补页面测试，防止核心 UI 结构退化。
3. 最后做本地服务和截图级视觉验证。
