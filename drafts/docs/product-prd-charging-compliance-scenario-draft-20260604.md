# 收费合规专项审计场景 PRD 草稿

## 1. 定位

本场景是 `AI 医疗审计系统 V1.0 PRD` 的首个候选专项审计场景，用于验证从 HIS 脱敏数据到疑点、复核、底稿和报告的最小闭环。

当前状态是候选场景草稿。目标医院尚未提供真实 HIS DDL、字段字典、脱敏样本和历史复核验证集，因此本文只定义业务边界、输入契约、最小规则、输出证据包和验收口径，不把任何具体 HIS 表名或字段写成已确认事实。

## 2. 场景目标

候选主题：收费合规 / 重复收费与目录限制核验。

V1.0 最小目标：

- 从 HIS 脱敏收费明细、就诊、诊断、医嘱/处方和项目目录中生成任务级数据快照。
- 运行首个 `0/1` 规则，识别疑似重复收费或目录限制不匹配线索。
- 每条疑点输出原始数据、命中规则、计算过程和知识库依据。
- 审计员可从疑点创建复核任务，维护复核意见和结论。
- 已确认违规疑点可进入任务底稿、报告草稿、任务级正式报告签发、签发后整改跟踪、任务级结案门禁和关闭后只读锁定；报告草稿前必须登记外部附件清单或上传归档附件，签发后正式报告正文按 `sha256` 冻结，整改事项绑定正式报告编号和正文哈希，整改未验收前不得结案，结案后状态、附件、签发和整改写接口均被阻断并记录运行态操作日志。

## 3. 非目标

V1.0 首个场景不做：

- 实时连接 HIS 生产库。
- 复杂风险评分。
- 自动给出无依据审计结论。
- 多院多租户。
- LIS、PACS、财务系统联合审计。
- 医保结算清单全量复杂稽核。
- OCR 扫描件处理。

## 4. 用户流程

```text
信息科交付 DDL/字段字典/脱敏样本
-> 系统生成 HIS 数据质量报告
-> 审计员创建收费合规专项任务
-> 系统绑定数据快照和规则版本
-> 运行 0/1 规则
-> 输出疑点清单和证据包
-> 审计员复核疑点
-> 负责人确认
-> 登记附件清单或上传归档附件
-> 导出底稿/报告草稿
-> 签发并冻结正式报告
-> 生成并跟踪整改事项
-> 整改验收后结案
-> 结案后只读查看和导出
```

## 5. 最小数据输入

目标医院必须至少提供以下数据域。真实表名和字段名由院方 DDL 决定，系统仅定义标准字段契约。

| 数据域 | 必需性 | 用途 | 关键字段 |
| --- | --- | --- | --- |
| 就诊记录 | 必需 | 关联患者、科室、时间范围和收费明细 | 匿名患者 ID、就诊 ID、门诊/住院标识、就诊时间、科室、医生 |
| 诊断记录 | 必需 | 判断目录限制、病种和适应症 | 就诊 ID、诊断编码、诊断名称、主/次诊断、诊断时间 |
| 医嘱/处方 | 建议必需 | 判断收费项目是否有对应医嘱依据 | 医嘱/处方 ID、就诊 ID、项目编码、数量、频次、开立时间、执行时间 |
| 收费明细 | 必需 | 识别重复收费、超量收费和金额异常 | 收费 ID、就诊 ID、医院项目编码、医保项目编码、数量、单价、金额、收费时间、结算状态 |
| 项目目录 | 必需 | 关联医保目录和院内项目 | 医院项目编码、医保项目编码、项目名称、规格、单位、价格、生效日期 |
| 科室人员 | 必需 | 归属复核和整改责任 | 科室编码、科室名称、医生编码、医生匿名 ID |

## 6. 首批规则候选

首批只做可解释的 `0/1` 规则。每条规则必须能输出命中原因和原始记录定位。

| 规则编号 | 规则名称 | 判定逻辑 | 输出状态 |
| --- | --- | --- | --- |
| CHARGE-RULE-001 | 同就诊同项目重复收费 | 同一就诊、同一收费项目、同一服务日期或同一医嘱关联下出现多条收费，且不能被数量、频次、执行记录解释 | `suspected-violation` 或 `not-hit` |
| CHARGE-RULE-002 | 无医嘱依据收费 | 收费项目需要医嘱/处方支撑，但在同一就诊范围内找不到可关联医嘱/处方 | `needs-evidence` 或 `not-hit` |
| CHARGE-RULE-003 | 目录限制条件不匹配 | 收费项目存在医保目录限制条件，患者诊断、年龄、性别或就诊类型不满足条件 | `suspected-violation`、`rule-issue` 或 `not-hit` |

首个开发规则建议选择 `CHARGE-RULE-001`，因为它最依赖 HIS 结构化数据，最少依赖复杂医学语义判断。

## 7. 疑点证据包

每条疑点必须包含：

- `finding_key`：疑点编号。
- `audit_task_key`：审计任务编号。
- `audit_run_key`：规则运行批次。
- `data_snapshot_key`：数据快照版本。
- `rule_version_key`：规则版本。
- `knowledge_index_version_key`：知识库索引版本。
- `source_record_locator`：源表、源主键、源批次、标准化记录 ID。
- `calculation_trace`：重复分组、时间窗口、数量、金额和判定过程。
- `knowledge_evidence`：法规、目录或监管规则引用，包含 `chunk_id`、`source_package_version_key`、`index_version_key` 和原文 locator。
- `review_status`：复核状态。

缺少源记录定位、规则版本或知识依据的疑点不能进入正式报告正文。

## 8. 验收口径

### 8.1 开发期 fixture 验收

在没有院方脱敏样本前，使用合成 fixture 验收：

- 至少 3 条确认重复收费正例。
- 至少 3 条正常重复数量/频次反例。
- 至少 2 条数据缺失导致 `needs-evidence` 的边界样本。
- 同一 snapshot + rule version 复跑结果一致。
- 每条疑点可导出证据包 JSON。

当前开发期状态：

- 已新增 `CHARGE-RULE-001` 合成 fixture 和最小执行器。
- 已覆盖 3 个正例、3 个可解释反例、2 个 `needs-evidence` 样本。
- 已支持生成可写入 `audit_findings` 的疑点 payload 和 `finding_evidence_items` 规则依据证据项。
- 已接入开发期疑点清单页，支持展示疑点、导出疑点 JSON、从疑点创建复核任务。
- 已建立 HIS 输入契约第一批：交付批次、表结构版本、字段映射。
- 已建立收费合规字段映射校验器，覆盖必需字段缺失、重复目标字段、必需字段 nullable、敏感字段缺失脱敏规则。
- 已建立 HIS DDL 自动解析器和 CLI `his-ddl-parse`，可解析离线 DDL 的表、字段、主键、时间字段、字段注释和 DDL hash。
- 已建立 HIS 脱敏样本质量报告 CLI `his-sample-quality`，可在写入 staging 前检查 CSV/JSONL 样本字段对齐、必填空值、重复主键和行数字段画像。
- 已建立 HIS 脱敏样本 raw staging 导入 CLI `his-staging-import`，样本质量报告、source batch 和 table schema 通过后可写入 `his_staging_rows`，保留原始行、行号、row hash 和文件来源。
- 已建立 `CHARGE-RULE-001` staging 标准输入转换器，可从 `his_staging_rows` 和 `his_field_mappings` 构造 `ChargeDetailRecord`，并复用现有规则执行器输出疑点和 `needs_evidence`。
- 已建立 HIS 数据快照计划 CLI `his-snapshot-plan`，样本质量报告通过后可生成 `AuditDataSnapshotCreate` payload、row_counts 和快照 checksum。
- 已建立 HIS 数据快照受控入库 CLI `his-snapshot-apply`，默认 dry-run，显式 `--execute` 后写入 `audit_data_snapshots`，并在写入前校验项目存在性和 `snapshot_key` 唯一性。
- 已建立 `charge-rule-001-staging-run` CLI，可从 HIS staging 行运行 `CHARGE-RULE-001`，默认 dry-run，显式 `--execute` 后写入 `audit_findings` 和 `finding_evidence_items`。
- 已建立 `his-snapshot-rollback-audit` CLI，可在生产 staging 验收失败时先计算快照回滚影响面，显式 `--execute` 后写入 `audit_snapshot_rollbacks` 审计事件。
- 已建立 `his-staging-acceptance` CLI，可只读验收生产 staging 链路，输出 PASS/FAIL 报告和 JSON 证据，不写生产库。
- 已建立 `case-review-report-gate` CLI，可在正式报告生成前只读校验疑点证据、复核任务、复核状态、复核意见/结论、确认违规底稿和负责人确认。
- 已在复核任务台接入任务级报告准备度预检、承办人、底稿状态和负责人确认记录。
- 已在复核任务台接入附件清单登记、服务端附件文件归档、报告草稿 Markdown/JSON 导出、正式报告签发冻结、签发后整改跟踪、任务级结案门禁和关闭后只读锁定。当前归档文件保存到服务端索引根目录下的任务附件区，签发能力保存冻结 Markdown 正文和 `sha256`，整改事项绑定已签发报告编号和正文 `sha256`，整改未验收前不得结案，结案后状态、附件、签发和整改写接口均返回 `409` 并记录 `review-task-readonly-write-blocked` 运行态操作日志，仍未接入对象存储、病毒扫描、电子签章、独立整改数据库表、持久化审计日志或附件级权限隔离。
- 该结果只证明工程闭环，不证明院方真实数据准确率。

### 8.2 院方样本验收

拿到脱敏历史数据和验证集后，验收口径必须由院方确认：

- 准确率按疑点条目、处方、患者、病例或收费明细中的哪一类计算。
- 抽样方法、样本量和复核责任人明确。
- 误报、漏报、规则争议、数据缺失分别统计。
- 无法判定项进入 `needs-evidence` 或 `rule-issue`，不得静默归为正常。

## 9. 依赖与阻塞

进入正式规则开发前必须完成：

- HIS DDL 和字段字典交付。
- 脱敏收费明细、就诊、诊断、医嘱/处方、项目目录样本交付。
- 院方确认 `CHARGE-RULE-001` 的时间窗口、重复判定口径和可排除情形。
- 院方提供或确认验证集样本。
- 报告模板和签字流程确认。
