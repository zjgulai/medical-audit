# 知识库查询引擎方案草稿

## 1. 首版目标

首版知识库查询引擎定位为 `检索 + 引用型问答 + 原文定位`。

它先服务审计员查法规、政策、规则、医保目录依据，不直接输出合规判定结论。合规判断能力后续基于知识底座和结构化规则引擎叠加。

## 2. 部署与模型边界

- 开发期先使用云端 API 快速验证 embedding、rerank 和答案生成效果
- 交付版按私有化部署设计
- 知识库、索引库、文档元数据和引用链必须本地保存
- 云端 API 开发期不得上传患者数据
- 模型调用层必须保留替换为私有化模型的接口边界

## 3. 首版索引范围

首版优先索引：

- 医保目录
- 智能监管“两库”规则和知识点
- 风险负面清单
- 医保相关法律

`全量法律` 不做无差别全量索引，只抽取医保、医疗、药品、基金监管、处方、门特、DRG/DIP 等相关文本进入首版索引。

## 4. 知识库组织方式

- 按业务来源分集合管理
- 查询入口统一，不要求用户预先选择知识库
- 检索排序时按业务场景对来源加权
- 每条答案必须保留来源集合、原文件、页码/章节/条款等追溯信息

首版集合包括：

- `medical-insurance-catalog`
- `supervision-rules-knowledge`
- `risk-negative-list`
- `medical-insurance-laws`

## 5. 检索策略

首版采用 `关键词检索 + 向量检索 + rerank + 元数据过滤`。

- 关键词检索负责精确术语、文件名、政策号、条款号召回
- 向量检索负责自然语言语义召回
- rerank 负责对混合召回结果重新排序
- 元数据过滤负责限制来源、年份、地区、资料类型、业务主题

## 6. 技术栈基线

开发期基线采用：

- `Python`
- `FastAPI`
- `PostgreSQL`
- `pgvector`
- `Tantivy/BM25`

职责边界：

- `FastAPI` 提供查询、索引、重建、健康检查接口
- `PostgreSQL + pgvector` 存文档元数据、chunk、向量和引用关系
- `Tantivy/BM25` 做本地关键词检索
- 云端 API 用于开发期 embedding、rerank、answer generation 验证
- 规模上来后再评估是否替换或补充 `OpenSearch`

### 6.1 模型 Provider 策略

- 模型调用层统一抽象为 provider 接口
- 开发期优先使用 `OpenAI API` 验证 embedding、rerank 和 answer generation 效果
- 代码层必须预留国产模型和本地私有化模型适配点
- 业务逻辑不得直接依赖某个具体模型厂商的 SDK
- 交付版可在不改动检索、引用和索引核心逻辑的前提下替换模型 provider

### 6.2 本地开发数据库

- 本地开发环境使用 `Docker Compose` 启动 `PostgreSQL + pgvector`
- 开发机不要求直接安装 PostgreSQL
- 项目需提供本地数据库初始化脚本和 schema 初始化说明
- 测试环境应支持独立测试数据库，避免污染开发库

## 7. 切分与引用粒度

- 法规政策按章、节、条款结构切分
- 普通文档按标题层级和段落切分
- 表格资料按行或规则项切分
- 每个 chunk 必须保留可追溯定位信息，包括原文件、来源集合、标题层级、条款号、页码或行号

## 8. 答案形态

查询接口返回结构必须包含：

- 答案正文
- 分条依据
- 引用片段
- 原文定位
- 置信提示

答案不得只返回大模型生成文本。用户必须能从每条结论回到原始资料位置。

## 9. 跨来源综合方式

- 允许跨集合综合回答
- 答案必须区分法规依据、规则依据、目录依据、风险案例依据
- 不允许把不同来源类型混成无来源差异的一段结论
- 每条依据都必须保留独立引用和原文定位

## 10. 原文定位打开方式

- 系统内提供原文预览
- 原文预览必须高亮命中片段
- 引用必须能定位到页码、条款、章节或表格行
- 系统同时保留本地源文件路径，便于审计留档和人工核验

## 11. 检索评测集来源

首版评测集由三类问题混合构成：

- 审计员真实问题
- PRD 场景问题
- 资料标题、条款、规则项自动生成问题

评测集必须绑定期望召回资料、期望来源类型和答案可接受标准。评测目标不是只看答案流畅度，而是验证召回是否准确、引用是否正确、原文定位是否可核验。

## 12. 首版查询权限

- 审计科可完整查询知识库
- 信息科可管理索引任务、数据源状态和重建操作
- 被审计科室只能查看与自身整改事项相关的引用依据
- 查询、预览、导出和索引管理都必须留下操作日志

## 13. 索引重建机制

- 支持新增、修改、删除文件的增量索引
- 支持信息科手动触发全量重建
- 每次重建必须生成独立索引版本
- 重建前后必须支持版本对比，包括文件数量、chunk 数量、失败文件、来源集合变化和检索评测结果变化
- 查询结果必须能追溯到对应索引版本

## 14. 数据更新与版本管理方式

- 资料包采用版本化管理
- 每次导入生成 `source_package_version`
- 旧版本资料保留可追溯
- chunk、索引版本、答案引用都必须能追溯到对应资料包版本
- 不允许直接覆盖旧资料后丢失来源链

## 15. 首版接口形态

- 提供后端 API
- 提供最小查询页面
- 提供索引管理页面
- 查询页面用于自然语言检索、引用答案、原文预览
- 索引管理页面用于查看数据源状态、触发增量索引、触发全量重建、查看索引版本和失败文件

### 15.1 页面技术路线

- 首版使用 `FastAPI` 服务端模板实现最小查询页面和索引管理页面
- 首版页面只用于验证查询、引用、原文预览和索引管理闭环
- 后续产品化 UI 再迁移到 `React/Next.js`
- 后端 API 从首版开始保持前后端解耦，避免后续迁移时重写核心能力

## 16. 索引失败文件处理方式

- 索引失败文件进入失败队列
- 失败队列展示文件路径、来源集合、错误类型、错误摘要和失败时间
- 支持修复后单文件重试
- 失败文件不进入可查询索引
- 索引版本报告必须统计失败文件数量和失败原因分布

## 17. OCR 边界

- 首版处理可抽文本 PDF
- 扫描件和图片进入待处理队列
- OCR 不进入首版交付范围，放入 V1.1
- 待处理队列需记录文件路径、来源集合、文件类型、待处理原因

## 18. 首版管理后台范围

首版管理后台包含：

- 数据源状态
- 索引版本
- 重建任务
- 失败队列
- 待处理队列
- 评测结果

管理后台面向信息科和系统管理员，不面向普通被审计科室用户。

## 19. 实施前资料质量审计

- 进入工程实现前，先对 `data/` 做一次全量只读扫描
- 扫描范围覆盖 Markdown、PDF、xlsx、txt、zip、rar、png 等现有文件类型
- 输出资料质量审计报告，识别可索引文件、待处理文件、失败高风险文件、重复文件和命名异常
- 资料质量审计报告进入 `drafts/analysis/`
- 未完成资料质量审计前，不启动知识库引擎代码实现
