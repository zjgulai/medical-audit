## P0 — 整改工作台真实 case ID 映射

### P0-1 整改附件上传绑定真实 remediation_items UUID

**现状**：前端 `AttachmentUploadButton` 收到的是 workbench API 返回的静态 case id（如 `remediation-case-001`），而后端 `uploadRemediationAttachment` 路由期望 `remediation_items.id`（UUID）。两者不匹配会导致附件上传 404 或写入错误 item。

**修复方案**：
- 后端 `GET /api/v1/remediation/items` 的结果应与 workbench 的 cases 数组合并展示
- 前端整改工作台优先从 `/api/v1/remediation/items` 获取真实 item 列表（已有 API），workbench 作为摘要补充
- `AttachmentUploadButton` 使用真实 `item.id`（UUID）

**文件**：
- `src/medical_audit_kb/api/routes_workbench.py`（remediation_workbench 关联真实 item id）
- `web/src/components/replica/replica-remediation-workbench.tsx`（加载真实 items 列表）

**工作量**：中（前后端各改 1 个函数，约 1-2 小时）

---

### P0-2 整改工作台加入状态更新操作

**现状**：工作台只能查看状态和上传附件，无法直接更新整改状态（如：从"待整改"推进到"整改中"，或提交验收）。审计员完成整改后找不到操作入口。

**修复方案**：每个整改事项加「更新状态」下拉或快捷按钮：
- 「开始整改」→ `in-rectification`
- 「提交验收」→ `pending-acceptance`
- 「关闭」→ `closed`

调用已有的 `POST /api/v1/remediation/items/{id}/status` 路由。

**文件**：`web/src/components/replica/replica-remediation-workbench.tsx`

**工作量**：中（前端约 2 小时，需要新增 api-client 调用 + 状态更新 UI）

## P1 — 报告签发持久化

### P1-1 报告签发状态写入 DB

**现状**：`POST /reports/drafts` 可创建草稿，但签发状态（`is_signed_off`、`signed_at`、`signer`）未持久化到 DB，页面刷新后丢失。

**修复方案**：
- 在 `review_tasks` 表新增字段：`is_signed_off BOOLEAN DEFAULT FALSE`，`signed_at TIMESTAMPTZ`，`signed_by TEXT`
- 或新建 `report_signoffs` 表（更干净，不污染 review_tasks）
- 暴露 `POST /api/v1/reports/drafts/{id}/signoff` 路由

**工作量**：中（schema migration + store 层 + 路由，约 3-4 小时）

---

### P1-2 报告工作台签发 UI

**现状**：`/reports` 页面有草稿创建，但无签发操作按钮。

**修复方案**：已有草稿的报告卡片加「签发」按钮，调用 P1-1 新增路由；签发后显示签发人 + 时间戳。

**文件**：`web/src/components/replica/replica-report-workbench.tsx`

**工作量**：小（约 1 小时，依赖 P1-1）

## P2 — 审计助手对话历史持久化

### P2-1 chat 对话历史写入 DB

**现状**：`/chat` 页通过 `?history=` URL 参数传递上下文，但对话记录不持久化。用户刷新页面后历史消失。

**修复方案**：
- 已有 `query_history` 表（`QueryHistoryStore`），对话结果已写入
- 前端加载时从 `GET /api/v1/history` 拉取最近 N 条对话，渲染为历史消息
- 新对话写入时用已有 `POST /api/v1/query` 路由（已存 DB）

**工作量**：中（前端约 3 小时，读取 + 渲染 query_history）
